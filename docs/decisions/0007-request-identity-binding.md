# 0007 请求身份绑定与写接口令牌

- 状态：已采纳（M4 安全修复）
- 日期：2026-10-23
- 相关：`src/qf_wire/config/usertoken.py`、`src/qf_wire/web/server.py`、`src/qf_wire/cli/token.py`、`tests/integration/test_dashboard_api.py`、`tests/unit/test_web_guard.py`、`tests/unit/cli/test_token.py`、`docs/DEPLOYMENT.md`
- 取代：`0005-multiuser-and-api-auth.md` 第 3 条（身份来源）与第 8 条（写接口只要求 `X-Wire-Request`）

## 背景

安全审计在本机复现了两个问题：

- **SEC-03**：多用户模式下，`X-QF-User` 只经过格式校验就被当作身份。bob 的看板实例收到 `X-QF-User: alice` 后，直接返回了 alice 的 `data.js`（1,749,854 字节 vs bob 自己的 116 字节）。用户 id 合法不等于请求者就是该用户。
- **SEC-01**：写接口（保存模型配置、触发生成）只要求回环地址和固定头 `X-Wire-Request: 1`。这个值写死在页面源码里，本机任何网页/脚本都能构造，等于没有身份校验。

需要在不破坏“本机开箱即用”和单用户默认行为的前提下，把“选择用户”和“证明身份”分开。

## 决策

1. **实例绑定用户是匿名身份**：`QF_WIRE_MULTIUSER=true qfw serve --user alice` 启动的实例只服务 alice。浏览器不需要任何自定义头；携带 `X-QF-User` 指向其他用户一律 403。绑定用户在服务端配置里，不接受客户端覆盖。
2. **共享实例的选择必须配凭据**：不带 `--user` 启动的多用户实例，`X-QF-User` 只负责选择目录，必须同时提供 `X-QF-User-Token`，其值与 `<base_data>/users/<id>/api.token` 做常数时间比较。缺失或不匹配返回 401，不回落到默认用户、不提示“用户是否存在”。
3. **凭据由 CLI 生成**：`qfw token --user <id>` 首次生成并落盘，重复执行复用；`--rotate` 轮换，旧值立即失效。文件权限尽力设为 `0600`（Windows 上依赖用户目录 ACL）。凭据不写入配置、不进入 git。
4. **写接口三层校验**：回环地址 + `X-Wire-Request: 1` + `X-QF-Write-Token`。写令牌在 `qfw serve` 启动时用 `secrets.token_urlsafe(32)` 生成，服务端注入看板页面的 `<head>`（`window.QF_WRITE_TOKEN`），页面请求自动携带；脚本场景可用 `QF_WIRE_WRITE_TOKEN` 固定。
5. **校验 Host 头**：绑定具体地址时，`Host` 必须是 `127.0.0.1:<port>`、`localhost:<port>`、`[::1]:<port>` 或监听地址之一，否则 403；监听 `0.0.0.0`/`::` 时跳过（允许反向代理自定义域名）。
6. **单用户模式行为不变**：未开启多用户时，`X-QF-User` 不影响目录，也不要求凭据；回环读取仍免 token。

## 理由

- 用“实例绑定 + 凭据选择”替代“请求头即身份”，把攻击面从“谁都能选的字符串”缩小到“本机文件系统里的随机值”；
- 绑定用户的实例保持零配置，覆盖绝大多数使用方式（一人一机、一人一实例）；
- 写令牌由页面下发，满足“浏览器跨站无法读取页面内容、也无法伪造自定义头”的既有约束，同时不引入登录体系；
- `Host` 校验补上 DNS rebinding 的缺口：攻击者域名解析到 127.0.0.1 时，浏览器发出的 `Host` 仍是攻击者域名；
- 凭据是每用户独立文件，泄露一个用户不波及其他用户，轮换也不需要重启服务。

## 被否方案

| 方案 | 否因 |
| --- | --- |
| 继续只校验 `X-QF-User` 的格式 | 格式合法与身份真实无关，SEC-03 的 PoC 就是这样打穿的 |
| 所有用户共用一个全局 token | 一个用户泄露等于全部用户泄露，失去隔离意义 |
| 引入登录页 / Cookie 会话 | 需要用户体系、会话存储与密码管理，超出“本地优先、无云端账户”的产品边界 |
| 回环读取也强制 `QF_WIRE_API_TOKEN` | 破坏本机零配置体验，且无法解决写接口被本机程序伪造的问题 |
| 只在反向代理层做身份校验 | 直接运行 `qfw serve` 的用户没有代理，漏洞仍然存在 |

## 代价与风险

- 共享实例需要给每个用户分发 token，运维步骤比“直接发用户 id”多一步；
- 写令牌只防跨站伪造与本机误触发，不防本机恶意进程——能读进程环境或用户目录的程序本来就能拿到凭据；
- Windows 上 `chmod 0600` 不生效，凭据安全性依赖用户目录 ACL；多用户共享系统账户的场景无法提供强隔离；
- 绑定用户的实例不能通过请求头切换身份，需要跨用户查看时必须另起实例或改用共享实例 + 凭据。
