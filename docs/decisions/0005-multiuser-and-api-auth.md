# 0005 多用户目录布局与只读 API 鉴权默认值

- 状态：已采纳（M4）
- 日期：2026-10-23
- 相关：`src/qf_wire/config/loader.py`、`src/qf_wire/web/server.py`、`src/qf_wire/core/jobs.py`、`tests/unit/config/test_multiuser.py`、`tests/unit/test_web_guard.py`、`docs/DEPLOYMENT.md`

## 背景

M4 要同时满足三件事：默认本机可用、可选多用户隔离、可选对外提供只读 API。三者会互相影响——多用户需要选择用户的入口，对外 API 需要鉴权，而默认行为必须保持“开箱即用、不额外配置”。需要确定用户目录如何组织、身份从哪里来、鉴权在什么条件下生效。

## 决策

1. **用户目录固定在数据目录下**：`<data>/users/<id>/{config/,wire.db,archive/,data.js}`。每个用户的数据库、归档与看板产物完全独立，不共享写路径。
2. **用户 id 是受限 slug**：`^[A-Za-z0-9_-]{1,64}$`。缺失、含 `/`、`..`、空格、中文或超长一律拒绝；请求阶段返回 400，CLI 阶段抛配置错误。路径拼接后再次校验位于用户根目录内。
3. **身份由宿主提供**：API 用 `X-QF-User`，CLI 用 `--user` 或 `QF_WIRE_USER`。多用户开启且缺少身份时报错，不猜测默认用户；Wire 自身不做登录与账户体系。
4. **用户配置三件套齐全才生效**：用户目录 `config/` 同时存在 `topics.yaml`、`sources.yaml`、`digest.yaml` 才使用，否则回落到全局配置，避免半套配置产生隐性差异。
5. **配置损坏不回退到别人的目录**：多用户模式或显式指定用户时，配置重载失败直接抛错；只有单用户模式才回落到启动时配置。
6. **读接口默认只允许回环**：以 socket 对端地址判断，不信任 `X-Forwarded-For`。`/api/health` 公开。
7. **token 是可选增量，不改变默认**：设置 `QF_WIRE_API_TOKEN` 后，非回环请求需 `Authorization: Bearer`；回环默认仍免鉴权，`QF_WIRE_API_REQUIRE_TOKEN=1` 可强制全部鉴权。私网地址必须额外打开 `QF_WIRE_ALLOW_PRIVATE_NETWORK=1`。
8. **写接口只服务本机页面**：仅 `POST /api/settings` 与 `POST /api/digest/run`，要求回环且带 `X-Wire-Request: 1`，不提供跨域写入。
9. **调度失败不拖垮进程**：单个任务异常被捕获并记日志，调度器继续运行；配置层面的错误（坏 cron、坏时区、未知命令）在启动时直接拒绝。

## 理由

- 目录布局与用户 id 规则让隔离边界可以用一条路径规则表达，测试与审计都容易验证；
- 身份交给宿主，符合“无云端账户、数据不出本机”的产品边界，也避免自建一套脆弱的登录体系；
- 默认回环 + 可选 token，让本地用户零配置，同时给内网/容器场景留出显式开关；
- 写接口加自定义头，利用浏览器跨站无法伪造自定义头的特性，挡住 CSRF；
- 配置错误启动即失败，比运行到一半才发现 cron 写错更容易定位。

## 被否方案

| 方案 | 否因 |
| --- | --- |
| 多用户默认取系统用户名 | 隐式选择会让“忘记带用户头”变成读到别人数据，风险高于便利 |
| 用户配置缺一件也生效（合并全局） | 同一用户不同启动方式可能读到不同配置，难以复现 |
| 默认对所有请求要求 token | 破坏本机零配置体验，且本地页面写入需要额外注入 token |
| 用 `X-Forwarded-For` 判断是否本机 | 头部可伪造，反向代理未清洗时会绕过限制 |
| 写接口用 CORS 白名单替代自定义头 | CORS 只约束浏览器读取，不能阻止简单请求提交 |

## 代价与风险

- 多用户身份依赖宿主正确注入，直接公网暴露前必须由反向代理完成鉴权与 TLS；
- 静态 Bearer token 没有过期与轮换机制，泄露后只能改环境变量并重启；
- 用户目录与全局配置的回落规则需要在文档中明确，否则运维容易误以为用户配置已生效；
- SQLite 仍是单文件多进程写入模型，调度与看板同机运行时依赖 WAL，未来水平扩展需要重新设计。
