QuotaFuse Wire 升级文档 v1.0
产品名：QuotaFuse Wire
中文名：QuotaFuse 资讯线报
PyPI 包名：quota-fuse-wire
Python 包：qf_wire
CLI 主命令：qfw
CLI 长别名：quota-fuse-wire
定位：QuotaFuse 产品线的资讯感知层——多源采集、AI 提炼、事件聚合、全程本地、可被 Council 与任意 MCP 客户端消费。
边界：只做资讯采集与提炼，不做交易信号，不输出买卖建议。

兼容策略：保留旧仓库名和旧脚本入口作为过渡别名，README 标注“已升级为 QuotaFuse Wire”，已有用户 git pull 后仍可按原方式运行。

一、升级背景与定位
1.1 早期版本现状
早期版本是一个刻意保持极简的自包含工具：

核心逻辑平铺在根目录：fetch.py、digest.py、server.py、index.html；

纯 Python 标准库抓取，用户自己的模型做提炼，数据不出本机；

输出 data.js 给看板；

适合个人每日使用，工程化和生态连接较弱。

1.2 升级定位
QuotaFuse Wire 不是把早期版本做重，而是在保留“零强制 API key、全程本地、自包含”核心优势的前提下，分阶段增强：

工程健壮性；

采集与分析深度；

与 QuotaFuse 生态的集成；

按需产品化部署。

1.3 在 QuotaFuse 产品线中的位置
text
QuotaFuse StockData   → 数据底座（行情、财报、公告、资金、风险事件）
QuotaFuse Wire        → 资讯感知层（新闻、政策、产业链、多源聚合、AI 提炼）
QuotaFuse Council     → 投研合议层（多角色分析、辩论、回测、告警、报告）
职责：Wire 供资讯，StockData 供数据，Council 做决策。三者通过统一 DataEnvelope 和 MCP 工具解耦，不重复建设。

二、升级原则
保留内核：纯本地、无强制托管依赖、无强制 API key、数据不出本机；

增强外围：模块化、并发采集、事件聚合、信源评分、配置化赛道；

生态连接：作为 Council 的资讯 Provider，输出 MCP 工具，与 StockData 字段契约对齐；

保护资产：极简和本地优先是卖点，不因升级引入重型中间件或云端账户；

兼容旧用：旧脚本入口和旧数据格式在过渡期继续可用。

四、分阶段升级路线
阶段一：工程健壮性（M1）
目标：结构清晰、单源失败不拖垮全局、历史可回溯，使用方式不变。

升级项：

模块化重组

text
src/qf_wire/
├── core/          # 调度、清洗、去重
├── sources/       # 各信息源适配器
├── pipeline/      # 采集→清洗→提炼→输出
├── digest/        # AI 提炼
├── render/        # 看板渲染
├── cli/           # qfw 入口
├── mcp/           # MCP Server
└── config/        # 赛道与源配置
入口仍保留 python fetch.py 和 qfw run 两种方式。

采集健壮性
每个源独立超时、重试、降级标记；单源失败时看板标注“该源今日不可用”，整体流程不中断。

数据持久化
在 data.js 之外增加按日期归档的轻量 SQLite 或 Parquet，支持回溯和增量对比。

配置化赛道与源
将 12 大赛道和 100+ 源从硬编码迁移到 topics.yaml / sources.yaml，用户可自行增删赛道和 RSS 源，无需改代码。

验收：

单源失败不影响其他源；

历史数据可查询；

用户可通过配置新增赛道和源；

旧 python fetch.py 用法仍可用。

阶段二：采集与分析深度（M2）
目标：更快、更聚合、更有信源质量意识。

升级项：

异步并发采集
用 asyncio + aiohttp 替代同步抓取，100+ 源拉取时间从分钟级压缩到秒级，不引入外部框架。

事件聚类与故事线
对同一事件被多家源报道的情况做轻量聚类（标题相似度 + 实体提取），在看板中折叠为“多源 N”标签，并生成事件时间线。

信源质量评分
记录每个源的历史准确率、时效性、重复率，在要点生成时给予权重，并在 UI 中展示信源可信度标记。

可配置提炼策略
digest.yaml 支持按赛道配置 prompt、模型、输出结构；仍使用用户自己的模型。

验收：

采集速度显著提升；

同一事件可见多源聚合视图和时间线；

信源评分可在看板查看；

提炼策略可按赛道配置。

阶段三：QuotaFuse 生态集成（M3）
目标：从独立工具升级为生态中的资讯感知层。

升级项：

作为 Council 的资讯 Provider
将 Wire 产出封装为 DataEnvelope 兼容的 WireProvider，注册进 Council 的 DataAccessLayer。Council 的新闻分析师、政策分析师直接消费结构化资讯，带 source、freshness、confidence 溯源字段。

复用生态模型网关
digest 可接入 StockData/Council 统一的 model_gateway 配置，模型选择、重试、降级由底层处理，但仍保留“用户自己的模型”原则，只是调用路径统一。

与生态资讯模块对齐
源清单、赛道定义、提炼 prompt 与生态内资讯雷达模块保持一致性，避免重复维护。

输出 MCP 工具
暴露工具：

wire_get_digest(topic, date)：获取某赛道某日要点；

wire_search_events(keyword, window)：查询事件多源报道；

wire_get_timeline(event_id)：获取事件时间线；

wire_list_sources()：列出信源与质量评分。
任何支持 MCP 的 Agent 客户端可直接调用。

验收：

Council 可通过标准接口获取 Wire 资讯；

MCP 客户端可列出并调用 Wire 工具；

源列表与生态其他项目一致；

Wire 输出带完整溯源元信息。

阶段四：产品化与部署（M4，按需）
目标：从小团队可用，不破坏本地优先。

升级项：

Docker Compose 一键部署：抓取、看板、定时任务打包，降低非 Python 用户门槛；

只读 API：/api/digest?topic=semiconductor，方便其他系统集成，默认仅本机；

多用户隔离：每人独立配置和 SQLite 目录，不引入云端账户；

定时调度：内置 APScheduler 或系统 cron 模板，每日自动抓取和提炼。

验收：

Docker Compose 可一键启动；

只读 API 默认本机监听，可配置鉴权；

多用户配置隔离；

定时任务可配置。

五、CLI 设计
bash
# 采集与提炼
qfw run                          # 全量采集 + 提炼 + 输出
qfw run --topic semiconductor    # 只跑指定赛道
qfw run --sources-only           # 只采集不提炼
qfw digest --date 2026-10-22     # 对指定日期数据重新提炼

# 看板
qfw serve --port 8790            # 启动本地看板

# 信源与赛道
qfw sources list
qfw sources validate
qfw topics list
qfw topics add --file topics.yaml

# 历史与事件
qfw history --topic semiconductor --days 7
qfw event show <event_id>
qfw event timeline <event_id>

# MCP
qfw mcp stdio
qfw mcp http --port 8791

# 配置
qfw config validate
qfw config migrate               # 从早期版本旧配置迁移
输出规范：

结构化结果走 stdout，日志走 stderr；

支持 --output json|table|csv；

退出码：0 成功、2 参数错误、3 配置错误、4 源不可用、6 对象不存在、8 部分源失败；

qfw mcp stdio 的 stdout 只输出 MCP 协议报文。

七、数据契约
Wire 输出统一 WireEnvelope，与 Council 的 DataEnvelope 对齐：

python
class WireEnvelope(BaseModel):
    domain: str          # news / policy / industry
    topic: str
    event_id: str | None
    data_as_of: date
    payload: dict        # 要点、多源列表、时间线
    source: str          # wire
    source_detail: str   # 原始信源列表
    fetched_at: datetime
    freshness: str       # realtime / cached / archive
    confidence: str      # high / medium / low
    source_status: str   # ok / degraded / partial
八、与 Council / StockData 的边界
能力	QuotaFuse Wire	QuotaFuse StockData	QuotaFuse Council
新闻、政策、产业链资讯采集	✅	❌	❌
事件聚类、时间线、信源评分	✅	❌	❌
行情、财报、公告、资金、风险事件	❌	✅	消费
多角色分析、辩论、回测、告警	❌	❌	✅
MCP 工具	✅ 资讯类	✅ 数据类	✅ 分析类
运维面板	本地轻量看板	Admin Console	WebUI
原则：Wire 不重复实现行情和财报采集，Council 不重复实现资讯采集；三者通过 DataEnvelope 和 MCP 工具解耦。

九、不建议的升级方向
引入 Kafka 等重型消息队列：当前规模用 asyncio + SQLite 足够，Kafka 增加运维负担且违背自包含定位；

强制托管化/云端账户：破坏“数据全程留存本机、无托管依赖”的核心卖点；

把 AI 提炼改为纯规则抽取：跨源聚合提炼是 LLM 的优势，改为规则会降低产出质量；但数值和实体可用规则辅助；

输出交易信号或买卖建议：与 QuotaFuse 全产品线“不做实盘、不输出自动交易指令”的边界冲突。

十、测试与验收
10.1 测试类型
采集测试：各源正常、超时、空数据、格式变化；

并发测试：100+ 源并发采集耗时与稳定性；

聚类测试：同一事件多源聚合准确性；

信源评分测试：权重计算和展示；

配置测试：topics.yaml、sources.yaml、digest.yaml Schema 校验；

MCP 测试：stdio/http 客户端联调；

兼容测试：旧用法和配置迁移；

安全测试：默认本机监听、API 鉴权、敏感配置脱敏。

10.2 关键验收项
qfw run 可完成全量采集 + 提炼 + 输出；

单源失败不中断全局，看板标注降级；

历史数据可查询，事件时间线可用；

用户可通过配置新增赛道和源；

Council 可通过 WireProvider 获取资讯；

MCP 客户端可调用 Wire 工具；

旧用法在过渡期可用；

默认本机监听，无强制 API key。

十三、上线前核验项
核验 quota-fuse-wire、qf-wire、qfw 在 PyPI 和系统命令中是否可用；

交付结论：QuotaFuse Wire 的升级不是把早期版本做重，而是保留其“本地优先、自包含、无强制 API key”的核心资产，分四阶段增强工程健壮性、采集分析深度、生态集成和产品化能力。升级后，Wire 成为 QuotaFuse 产品线的资讯感知层，与 StockData、Council 形成“数据—资讯—决策”的清晰分工。
